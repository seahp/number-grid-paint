# 打包与上架

这份文档讲的是**把源码变成发布物**的全过程：谁进哪个包、两个平台上架要求差在哪、
出门前要跑哪几条命令、发完之后怎么回扫。它是这一轮（1.0.2）补上的——之前这些只写在开发仓库的
`SUBMISSION.md` 里，装完技能包的人看不到，于是"发布相关内容不够齐全"。

`SUBMISSION.md`（只在仓库里，从这一轮起**不再打进任何市场包**——它通篇是开发仓库路径，
收件人照着敲只会卡住）讲的是**这一轮实际发生了什么**、踩过哪些平台的坑；
本文讲的是**照着做就能复现**的流程。两者不要混着改。

## 1. 一份源码，三份产物

```bash
python3 scripts/make_dist.py            # 仓库里跑：检查 + 出 dist/
python3 scripts/make_dist.py --strict   # 仓库里：提交前最后一次，待办升级成阻断
python3 scripts/make_dist.py --samples  # 仓库里：顺带用无头浏览器导两张样张 PDF
```

产出：

| 产物 | 给谁 | 内容差别 |
| --- | --- | --- |
| `dist/repo/` | GitHub | 根目录放主产物 HTML，带全部开发脚本、`.gitignore`、`SUBMISSION.md` |
| `dist/skill/number-grid-paint/` | SkillHub zip 的目录形态 | 主产物挪进 `assets/`，带回归探针脚本，不带打包脚本（它只该在仓库里跑） |
| `dist/number-grid-paint-skillhub.zip` | SkillHub | 上面那份目录，`SKILL.md` 用**完整 15 字段** frontmatter |
| `dist/skill-lite/number-grid-paint/` + `…-openplatform.zip` | WorkBuddy 开放平台 | **不带 `scripts/`**（那边的静态检测会把 `subprocess.run` 报成「命令执行风险」），`references/` 只留讲出题口径的那一篇，`SKILL.md` 只留官方 9 字段，顶部加一条注释说明校验脚本在源码仓库里 |

zip 用 `zipfile` 手写：固定时间戳、清空 macOS 的 extra field、跳过 `.DS_Store` /
`__MACOSX` / `__pycache__`，所以**重复打包字节一致**，比对指纹才有意义。

## 2. 五个必须知道的坑

* **SkillHub 按扩展名过滤文件**：没扩展名的文件会 400 整包拒收（实测报 `不允许的文件类型: LICENSE`）。
  **图片也不收**：把仓库里那张截图 `assets/preview.png` 打进包，同样 400，报 `不允许的文件类型`。
  所以许可证叫 `LICENSE.txt`，
  `.gitignore` 只留在仓库，成品截图也只留在仓库——市场包里的文档改用它在 GitHub 上的
  绝对地址（`https://raw.githubusercontent.com/<仓库>/main/assets/preview.png`），
  写法见下一节的 `zip:only` / `zip:skip`。
* **开放平台按解压后字节数卡 3MB**（校验的是解压后字节，不是 zip 文件大小），
  并且会做静态代码检测。精简包因此不带脚本目录。
* **开放平台会机械解析 `SKILL.md` 里出现的每一条路径**，包里缺文件就直接驳回，
  不接受"这一行讲的是仓库"这种散文豁免。2026-11-15 的驳回原文：
  `资产包缺少必需资源 1 项：文件「scripts/pdf_export.py」（SKILL.md 引用）`。
  而精简包**又不能**带脚本，两个约束是反着的——唯一的解法是按布局分叉，见第 3 节。
* **两个平台的 frontmatter 字段集不一样**：本地 `SKILL.md` 写成**两处的超集**，
  打包时各自重写——SkillHub 要 `name/slug/display_name(_en)/displayName(En)/summary/tags/
  description(_zh/_en)/category/version/author/homepage`，开放平台只要官方那 9 个。
  多带字段、值里出现 ` & `、或 YAML 写法偏一点，都可能让它"解析失败"。
  顺带一句：SkillHub 详情页的「概述」渲染的是 `SKILL.md` **正文**，`homepage` 字段不展示，
  所以源码仓库地址要写在正文第一屏才看得见。
* **`.gitignore` 会静默掐断那条 raw 链接**：仓库的 `.gitignore` 里有 `*.png`，成品截图
  在本地存在、`git add` 却不报错，push 上去线上就是 404——而两个市场包的文档全靠这条链接。
  解法是在仓库那份 `.gitignore` 里给它开例外（`!assets/preview.png`），
  并由 `make_dist.py --strict` 里的 `check_raw_urls()` 兜住：文档里每一条 raw 地址都要
  同时满足"文件在 dist/repo 里、没被 .gitignore 挡住、已被 git 跟踪"，缺一不打包。
  注意判"是否被挡"要用不带 `-v` 的 `git check-ignore`——加了 `-v` 时否定规则也算命中，
  返回码会变 0，照着它判会得出"仍然被忽略"的错误结论。

## 3. 同一份源文档，按布局分叉

五个 HTML 注释标记（渲染时整段处理，纸面上看不到）。两个轴各管一件事：

| 标记 | 仓库 | 完整技能包 | 精简包 |
| --- | --- | --- | --- |
| `…` | 留 | 删 | 删 |
| `…` | 留 | 留 | 删 |
| `` | 删 | 删 | 只留这一段 |
| `…` | 留 | 删 | 删 |
| `` | 删 | 只留这一段 | 只留这一段 |

`repo:skip` 和 `zip:skip` 效果一样（都是"两个市场包都删、仓库留着"），分开写是为了说清
**为什么删**：`repo:skip` 是"这段讲的是开发流程"，`zip:skip` 是"这一版写法在包里会指向
一个包里放不下的东西"，后者总要配一段 `zip:only` 的替代写法。目前唯一的用例就是成品
截图：仓库里写本地路径 `assets/preview.png`（图就在仓库里），两个市场包里写它在 GitHub 上的
绝对地址——因为 SkillHub 不收图片文件。

用在 `SKILL.md`、`README.md`、`CHANGELOG.md` 和 `references/` 下的每一篇（打包时都过
`render_doc()`）。判断标准只有一条：**这一段提到的文件，收件人那个包里有没有**。
精简包带的是 HTML、README / SKILL.md / CHANGELOG.md / LICENSE.txt
和 `references/rules-and-generation.md`，所以指向别处的路径要么圈进 `lite:skip`，
要么换成一句不带路径的说法（例如"校验脚本在源码仓库里"）。

第 2 节第三条的反例就是被驳回那一轮：`SKILL.md` 的"批量出卷"写了
`python3 scripts/pdf_export.py …`，而精简包按设计不带脚本。现在那一段拆成两版：
精简包里给的是**地址栏参数**那套（`?copies=4&per=2&seed=…`，不用脚本也能一次出四份），
命令行导出的写法只留在完整技能包和仓库里。

分叉不是"藏起来"：精简包那份 `SKILL.md` 顶部有一条注释，明确说校验探针在源码仓库，
`## 7. 交付前自检` 也换成不开脚本就能做的三步（换一批看是否涂得完 → 回填种子比对 →
打印预览数页数）。收件人照它做，不会撞到"缺文件"，也不会以为我们没有自检。

## 4. 出门前：泄露与脱敏审查（纪律）

**任何一次对外动作之前都要跑它，退出码 0 才出门**——`git push`、市场上传、
`skillhub publish`、把链接发给别人，都算对外动作。这条是 2026-11-15 定下的纪律，
起因是另一个项目的公开仓库里混进过本班的真实数据，而当时所有功能测试都查不出来。

```bash
python3 scripts/leak_scan.py                 # 默认扫 dist/ 下三份目录 + 两个 zip 的包内字节
python3 scripts/leak_scan.py dist/repo       # 只扫要推上 GitHub 的那份
python3 scripts/leak_scan.py --strict        # 名单词表没声明也算失败
```

它查十类通用风险（本机路径、用户目录、账号名、邮箱、电话、证件号、token、私钥、
带凭证的 URL、UUID、教育类个人信息字段名），外加开发机上一份名单词表里你自己声明的词
——真实人名、班级、校名、内部代号这类**只有作者知道不能公开**的东西（词表叫
`redact_terms.txt`，它本身是敏感词集合，所以不打进任何包）。

三条设计值得记：

1. **命中行是打码打印的**（只留前 6 个字符 + 长度），否则审查报告本身会变成第二次泄露。
2. **豁免写在行内**：`# 审查例外：<理由>`。理由必须写，grep 得到，
   所以豁免是可审计的，不是"把规则关掉"。扫描器自己的正则字面量就靠这条通过。
3. **词表不出门**：名单词表只留在开发机，仓库里的打包脚本会专门检查它没混进发布物。
   在技能包里跑这条命令时，"缺词表"只是一句说明，不是"不要发布"；
   但**一条都没扫到一定算失败**——空扫描不等于干净，传了不存在的路径也直接退出码 1。

仓库里的打包脚本把这道审查串成了两道闸门：preflight 扫源码侧，打完包再扫**两个 zip 的
包内字节**（重写 frontmatter、剔除 `scripts/` 之后内容变了，只扫目录会漏）。

## 5. 文档与文件必须一致

评测里那句"照文档执行时容易卡住，需要先调整路径"，根因是文档提到的文件在**你所在的
那个布局里**不存在。三种布局的差别：

| | 开发仓库 / GitHub | 装好的技能包 | 精简包 |
| --- | --- | --- | --- |
| 主产物 | `数格涂涂_生成器.html`（根目录） | `assets/数格涂涂_生成器.html` | 同左 |
| 回归探针 | `scripts/` 全量 | `scripts/`（不含仓库专用的打包脚本） | **没有** `scripts/` |
| 发布文档 | `SUBMISSION.md` + `references/` 全量 | `references/publishing.md` 等四篇 | 只带出题口径那一篇 |
| `dist/`、`out/` | 有 | **没有** | **没有** |

`scripts/env.py` 和 `scripts/verify.mjs` 认前两种布局（主产物在根还是在 `assets/` 都找得到，
`env.py` 还会打印它认到了哪种布局），所以同一条 `node scripts/verify.mjs`
在仓库和技能包里都能直接跑，不需要先改路径。剩下那类"仓库里才有的命令"
在文档里出现时，**所在那一句必须带"仓库"字样**（英文写 repository 也认），
读者不会照着在技能包里敲。判定按**句子**不按物理行：中文折行是排版的事，检查器不该
逼着人把句子挤成一行，所以同一句里往回看两行；但句号、空行、新的列表项会断开——
上一句的"仓库"豁免不了这一句。这条规则本身带着四条自测断言，跑 `doc_check.py` 时先自测。

这条约束由 `scripts/doc_check.py` 守着，分两档：

```bash
python3 scripts/doc_check.py            # 查当前布局（在包里跑就查包，在仓库里跑就查仓库）
python3 scripts/doc_check.py --both     # 仓库 + 技能包 + 精简包三种布局都查
```

* `check_layout()` 是**读者视角**：把 README / SKILL.md / 各篇 references 里每条
  `scripts/<脚本>`、`assets/<文件>`、裸文件名和代码块里的 `python3|node …` 抠出来，
  逐个确认在对应布局里存在；仓库专用的那一句要带"仓库"标记（代码块不认折行豁免，
  但同一块里的 `#` 注释行可以承担说明）。
* `check_skillmd()` 是**平台视角**：只看 `SKILL.md`，**没有豁免**——提到的每条路径必须
  真在包里，渲染后还不许残留布局标记。这就是第 2 节那条驳回的机器版本。
* 顺带核对 `SKILL.md` 的 `version`、`CHANGELOG.md` 顶部条目、HTML 里的 `BUILD` 号是否对齐。

仓库里的打包脚本在 preflight 和打包尾部都会跑它（尾部对两个包各跑两档），
不一致就打不出 zip。所以**改完文档要重新打包**，别拿旧 dist 去上传。

## 6. 发布之后：把线上那份拉回来重扫

本地干净不等于线上干净——你推的可能是上一轮的旧 dist，市场也可能在上传时改写过文件。

```bash
python3 scripts/verify.mjs                        # 仓库里：确认源码态仍然 76/0
python3 scripts/doc_check.py --both               # 文档与三份布局仍然一致
python3 scripts/leak_scan.py dist                 # 包内字节
```

SkillHub 侧：`skillhub install number-grid-paint --namespace <你的命名空间> --dir <临时目录>`
装下来，对**下载回来的那份**再跑一次 `leak_scan.py` 和 `verify.mjs`，
并核对签名与内容指纹。发布当场 `install` 可能 404——安全扫描还在排队，
不是包坏了，等扫描过完再验。

**索引刷新要等十几分钟，别当场下结论**（1.0.2 实测）：`✓ Published` 之后头两次 `install`
拿到的仍是 1.0.0 的文件（17 个）、`search` 仍显示 1.0.1，第三次（约 15 分钟后）才翻到
1.0.2、22 个文件、与本地构建包 `diff -r` 逐字节一致。所以确认上线的方式是**轮询下载次数**
而不是重发新版本；判断"平台收到没有"看详情页 JSON 里的 `tags.latest`，那个字段先动。

顺带一句详情页那张成品图：仓库里的 `assets/preview.png` 用 `curl` 取是 200、1.6 秒，
而同一台机器在浏览器里首次加载同一张图超过 12 秒才出来。所以偶尔看到图空着多半是链路抖动，
不是链接坏了——判断以 `curl -s -o /dev/null -w '%{http_code}' <地址>` 为准，别因为一次
没显示就去动版本号。

还有个入口上的坑（1.0.1 这轮遇到）：后台「更新版本」里如果选了**复用当前版本**，
它拿的是线上已有的文件，于是提示"更新的包没有变化"——那是入口选错了，不是包坏了。
要发新内容就走 `publish <zip> --version <新号>`，让平台按包内容建新版本。
实在绕不开时才考虑"删条目重发"：代价是技能 ID 和详情页 URL 一起没了，
已经装过的人拿不到更新，引用过这条 URL 的地方（README、三个平台的简介）都要跟着改；
而且删除不可逆，动手前先确认后台能不能"下架旧条目 + 同 slug 重建"以保住 URL。

**被拒收的上传照样会把版本号占掉**（1.0.2 这轮实测）：那次 publish 把仓库里那张成品截图
也打进了包，报 `400 不允许的文件类型: assets/preview.png`，文件一个没上去；改好包再发同号，
又报 `slug 冲突: 版本 1.0.1 已存在`——线上那个 1.0.1 记录里装着的还是 1.0.0 的文件，
`install` 下来看 `SKILL.md` 的 `version` 就知道（写着 1.0.0）。
所以判断"线上到底是哪一版"别信版本号，**把包下载回来验内容**。补救是换一个新号发，
而不是删条目：号占了就占了，`CHANGELOG.md` 里留一句"跳过 1.0.1"就说得清。

GitHub 侧：`curl -sL https://github.com/<仓库>/archive/refs/tags/<tag>.tar.gz` 拉线上
tarball 重扫，别只看本地工作区。

## 7. 版本号怎么进位

* `SKILL.md` frontmatter 的 `version` —— 市场展示的那个号，也是 `doc_check.py` 对齐的基准。
* `CHANGELOG.md` 顶部条目 —— 必须和上面那个号一致。
* HTML 里的 `var BUILD`（状态条末尾的"代码版本 YYYY-MM-DD"）—— 改了版式或量测逻辑就进位，
  用来判断用户浏览器里挂的是不是旧标签页。它跟发布号不是一回事，可以同日多版本。

只改文档、工具、物料而没改产品行为的，进 patch 号；改了出题口径或版面算法的，进 minor。
**只要没问题就不用重发**——本地文档改动不值得推一个新版本，攒到下一次真改版一起带上。
反过来，评测或审核**明确指出的**"照文档执行会卡住""缺少必需资源"属于有问题，
不在"不用重发"之列：这类反馈应当成一次 bug 来修、来发版，别只补一张截图。
